# PreMortem AI — Domain Model

The domain model defines the canonical data structures that flow through the PreMortem AI pipeline.
Each entity is:
- Deterministic
- Schema-validated
- Strictly typed
- Designed for reproducible LLM inference

This model ensures consistency across extraction, scoring, clustering, mitigation generation, summarization, and final report assembly.

---

## 1. Core Entities Overview

PreMortem AI operates on six canonical domain entities:

  1. Risk
  2. Score
  3. Theme
  4. Mitigation
  5. Summary
  6. RiskReport (aggregate root)

These objects are produced sequentially through the pipeline and validated against their respective JSON Schemas.

Below is the high-level entity relationship diagram:

## 2. Entity Definitions

Each entity below includes:

- Purpose
- Required fields
- Canonical structure
- Notes on determinism, ID strategy, and schema expectations

### 2.1 Risk Entity

Purpose:

- Represents a potential failure mode extracted from unstructured text.
- Forms the foundational unit of all downstream analysis.

Identifier Format

`risk-xxxxx` (zero-padded deterministic integer)

Canonical Structure

```json
{
  "risk_id": "risk-00012",
  "title": "Ambiguous ownership of API integration tasks",
  "description": "Project lacks clearly defined ownership for the third-party API integration.",
  "category": "organizational",
  "source_text": "string segment used during extraction"
}
```

Notes

- IDs MUST be stable across retries to enable reproducibility.
- Source text is captured to support auditability.

### 2.2 Score Entity

Purpose:

- Quantifies severity via hybrid deterministic + LLM-assisted scoring.
- Used for ranking, aggregation, and theme formation.

Canonical Structure

```json
{
  "risk_id": "risk-00012",
  "likelihood": 4,
  "impact": 5,
  "severity": 20,
  "rationale": "Ownership gaps significantly increase delivery risk."
}
```

Notes

- Severity = likelihood × impact (unless overridden by rule-based logic).
- Rationale must remain concise and directly tied to the extracted risk.

### 2.3 Theme Entity

Purpose:
Groups related risks into higher-level patterns to provide leadership-level insight.

Identifier Format
`theme-xxxxx`

Canonical Structure

```json
{
  "theme_id": "theme-00003",
  "label": "Execution Readiness Gaps",
  "description": "Risks involving missing roles, unclear ownership, or incomplete planning.",
  "risk_ids": ["risk-00012", "risk-00028", "risk-00004"]
}
```

Notes

- Themes should NOT duplicate risk text — they abstract across risks.
- Membership lists must be stable for deterministic downstream behavior.

### 2.4 Mitigation Entity

Purpose:

- Provides actionable guidance mapped to risks + themes.
- Generated by LLM but normalized deterministically.

Canonical Structure

```json
{
  "mitigation_id": "mitigation-00009",
  "title": "Assign a single owner for API integration workstream",
  "actions": [
    "Designate a DRI for the integration.",
    "Define role responsibilities.",
    "Set weekly sync checkpoints."
  ],
  "risk_ids": ["risk-00012"],
  "theme_ids": ["theme-00003"]
}
```

Notes

- Actions must be imperative, clear, and auditable.
- De-duplication ensures consistent recommendations across retries.

### 2.5 Summary Entity

Purpose:

- Delivers a high-level executive narrative synthesizing risks, themes, and mitigations.

Canonical Structure

```json
{
  "health_score": 72,
  "top_risks": ["risk-00012", "risk-00028"],
  "narrative": "The project faces execution readiness challenges driven by unclear ownership..."
}
```

Notes

- Health score is deterministic: pipeline must define a stable formula.
- Narrative is LLM-generated but must remain schema-bound, concise, and reproducible.

# 3. Aggregate Root: RiskReport

Purpose:

- Final fully assembled object containing all normalized domain artifacts.

Canonical Structure

```json
{
  "risks": [...],
  "scores": [...],
  "themes": [...],
  "mitigations": [...],
  "summary": { ... },
  "metadata": {
    "generated_at": "2025-01-12T18:04:00Z",
    "model": "gpt-5.1",
    "schema_version": "1.0.0",
    "pipeline_run_id": "run-000023"
  }
}
```

Notes

- This object is the only output exposed externally.
- Must always pass `risk_report.schema.json` validation.
- Metadata ensures traceability and reproducibility.

# 4. ID Strategy & Determinism

To avoid nondeterministic LLM behavior:
- All IDs must be assigned after normalization, not during LLM inference.
- IDs must be sorted, zero-padded integers.
- Risk ordering must be stable — alphabetical or schema-defined.
- Themes and mitigations must derive from sorted inputs.
- No random UUIDs allowed in the domain model.

Determinism guarantees consistency across:
- Retries
- Model versions
- Cross-environment execution

---

# 5. Domain Rules

Risk Rules
- Must not exceed 2–3 sentences.
- Should describe a single failure mode.
- No overlapping or duplicated phrasing.

Scoring Rules

- Likelihood and impact are bounded 1–5.
- Severity must be explicitly derived.

Theme Rules

- Must represent abstract patterns.
- No one-to-one risk duplicates.
- Must contain at least two risks (unless exception documented).

Mitigation Rules

- Action verbs required.
- Each action must be independently testable.
- No vague or conceptual statements.

Summary Rules

- Narrative must not exceed ~150 words.
- Must reference themes, not raw risks.
